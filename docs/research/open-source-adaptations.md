# Open-source patterns adopted for M1

**Reviewed:** 2026-10-25
**Scope:** English voice loop with explicit local and optional hosted-provider modes; no telephony yet.

This note records upstream implementation strategies that address current failures. “Production-ready” is a project-specific claim and is not assumed from a repository's marketing or popularity. We reuse bounded, inspectable components and patterns, then keep the M1 stack small enough to measure. The user has clarified that hosted APIs are acceptable. Local inference remains available; provider choice must be explicit and local mode must never silently send data to a hosted service.

## Pipecat Smart Turn v3: semantic turn completion

- Upstream: [Pipecat Smart Turn documentation](https://github.com/pipecat-ai/docs/blob/main/api-reference/server/utilities/turn-detection/smart-turn-overview.mdx), [local ONNX implementation](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/audio/turn/smart_turn/local_smart_turn_v3.py), [model card and weights](https://huggingface.co/pipecat-ai/smart-turn-v3).
- Problem addressed: fixed silence thresholds cut off a caller who pauses mid-thought or make the exchange feel sluggish.
- Upstream strategy: maintain recent 16 kHz mono audio, classify whether the current pause ends the thought, and keep silence/VAD endpointing as a fallback. The v3 classifier accepts a recent eight-second audio window and can run on CPU.
- Reused here: the BSD-2 licensed CPU ONNX weights, Pipecat's BSD-2 feature extraction implementation (vendored with its header), and the eight-second windowing convention. The adapter is isolated behind `EndOfTurnDetector`; missing weights or inference errors fall back to the existing browser silence threshold.
- Deliberately not adopted: the full Pipecat runtime. The current single-process browser prototype needs one local classifier, not a new orchestration framework. If realtime transport, SIP, or multiple provider graphs become an M1/M2 requirement, reconsider adopting Pipecat's full pipeline rather than extending local glue.
- Validation so far: model loads in approximately 0.14 seconds and synthetic inference takes approximately 0.14–0.20 seconds on this environment. One generated eSpeak phrase crossed the 0.5 completion threshold with about 0.5 seconds of trailing silence. These are smoke measurements only, not human turn-taking accuracy results.

## Qwen3: conversation mode and decoding

- Upstream: [Qwen3 quickstart](https://github.com/QwenLM/Qwen3/blob/main/docs/source/getting_started/quickstart.md), [Qwen3 inference guidance](https://github.com/QwenLM/Qwen3/blob/main/docs/source/inference/transformers.md), [Qwen3 model repository](https://github.com/QwenLM/Qwen3).
- Problem addressed: short repeated stock responses and lack of awareness of the previous caller turn.
- Upstream strategy: use `/no_think` for non-thinking response mode and a non-thinking decoding setup around temperature 0.7, top-p 0.8, and top-k 20; presence penalty is an available repetition-control parameter.
- Reused here: the prompt now includes a bounded recent dialogue window (four exchanges maximum), removes the fixed unknown-hours example that was anchoring replies, and uses the documented non-thinking sampling values with a modest 0.3 presence penalty. `/no_think` changes the response mode; it does not turn inference off.
- Limits: a 0.6B model still has limited reasoning and can misrecognize speech. Context and sampler changes address repetition causes in this application; they do not establish accuracy or make business actions safe.

## Hosted API strategy approved for exploration

- **Gemini Live is the first voice-quality experiment to evaluate.** Google's current Live API supports 16 kHz PCM input, streamed 24 kHz PCM speech output, server WebSockets, automatic activity detection, and interruption events. The current Live API is marked Preview, and audio-only sessions have a documented 15-minute limit. The pricing table lists a free tier for Gemini 3.8 Live, but it also marks free-tier data as used to improve Google's products. Check the exact model access and quota on the user's API project before testing. Use synthetic prompts until the user has reviewed and approved sending microphone audio to Google.
- **Groq is a useful fast cascade comparison.** Its official API supports streamed chat completions and Whisper transcription uploads. The documented speech-to-text endpoints accept audio files, so they do not replace a continuous bidirectional voice session by themselves. Free account limits are model-specific and must be checked in the user's console.
- **OpenRouter is a model comparison route, not the default voice engine.** It offers OpenAI-compatible streamed chat completions and free models, but free plans have limited routing controls, availability/rate limits vary, and inputs are sent onward to a model provider. Provider retention/training policies vary; inspect the selected provider's policy for each model.
- Start with separate explicit config such as `VOICE_MODE=local|gemini_live`, and keep the existing local `ASR/LLM/TTS` chain unchanged. Add Groq/OpenRouter as explicit text/ASR alternatives behind existing interfaces only after baseline behavior is measured. Never fall back to a cloud provider after local errors without a user-selected mode.
- No provider keys are configured in the project process environment or project `.env` files at this review. The user says they have keys; keep secrets out of source control and add only empty `.env.example` placeholders when implementing a selected adapter.

## Current gaps and next research gate

- Validate turn detection, transcript accuracy, follow-up behavior, interruptions, and TTS naturalness on live microphone turns before adding more architecture. Compare local mode against an explicitly selected Gemini Live mode using the same synthetic and user-approved test phrases.
- The current Faster Whisper model is not a native streaming recognizer. Upstream alternatives such as Moonshine or sherpa-onnx should be compared on the same fixed phrase set for accuracy, CPU/RAM, and first-partial latency before replacement.
- Do not add a general voice framework, agent planner, vector database, or telephony dependency until measured M1 gaps require it. Reuse upstream code when its behavior, license, runtime, and data path fit the selected local or cloud mode.

## Comparative review: our project, receptionist apps, and frameworks

**This is a source review, not a deployment bake-off.** Public repository features and tests are evidence of implementation effort, not proof of production call quality. No external project below was installed or tested against our microphone, APIs, or target hardware.

### Where our project stands

The current project is a compact, local browser voice-loop prototype: FastAPI/WebSocket audio, browser speech activity detection, Pipecat Smart Turn v3, repeated Faster Whisper decoding for interim captions plus final transcription, a small local Qwen model, Kokoro speech, short in-memory context, and playback cancellation when the caller interrupts. The local code has explicit boundaries and is relatively easy to inspect and debug. Smart Turn is the only substantial runtime component adapted from a full voice framework.

Its demonstrated scope is much narrower than a phone receptionist. It has no SIP/PSTN connection, transfer to a human, persistent call records, voicemail workflow, calendar integration, or operational call dashboard. Its timing note (6.20 seconds mean across three synthetic local turns) is exploratory, and the roadmap still marks live microphone quality, p50/p95 latency, interruptions, and repeated-call reliability as unverified. Fifteen focused unit tests passed for the M1 update; these do not validate real callers, noisy rooms, or production load. Hosted-provider adapters are not yet implemented, even though future explicit cloud modes are now allowed by the project plan.

### Ranking by our actual goal

1. **For the next browser voice-quality experiment:** try Gemini Live through Pipecat or directly through the official Live API, against the same phrase set and turn scenarios as the local pipeline. This removes the slow local ASR → small LLM → local TTS chain and gives an end-to-end speech model; it may improve conversational timing, but has not been tested in this project. Gemini Live currently has documented session constraints and Google data-use terms that must be checked for the selected model/tier.
2. **For an extensible Python project with provider choice:** Pipecat is the strongest upstream candidate. First make a small isolated proof-of-concept on a branch, preserving the current local path, then compare turn accuracy, interruptions, first-audio latency, transcript quality, CPU/RAM, and failures. Do not migrate based on star counts.
3. **For a phone system with SIP and concurrency:** LiveKit Agents is the strongest framework candidate; Helix is the most directly relevant all-in-one feature reference. The decision depends on whether we want to own telephony operations or rely on LiveKit infrastructure.
4. **For receptionist business features:** Helix currently describes the broadest functionality of the reviewed application repos; that does not establish it as “best” without running calls and verifying the paths we need.
5. **For benchmark design:** borrow the per-turn instrumentation and scripted call methodology from the Conversation Relay reference, adapted to our chosen transport/provider and with measurements recorded on the actual target device.

**Overall assessment:** our project is currently a useful, understandable prototype and debugging surface, not yet competitive with those applications as a receptionist product. The biggest deficit is not that we lack a bigger “thinking model”; it is that our realtime path and quality have not been measured on real conversations, and the project has no phone/business-action layer. Pipecat is the most balanced next architecture to evaluate for this repo; LiveKit Agents may be better if phone deployment and concurrent sessions are now the priority. The best route is an evidence-based side-by-side prototype, not a wholesale rewrite based on repository claims.

### Provisional decision

Do not continue extending the current local prototype as the main product. Keep it as a diagnostics/reference harness. Before moving the project, perform a focused source and installability review of **LobbyStack** and **Tel-Agent**, and a small provider/telephony proof for **Patter + Gemini Live**. These represent the three viable trade-offs: complete MIT receptionist but OpenAI-specific live voice; broader SIP/model gateway but alpha and AGPL; or strongest Gemini Live/carrier match but SDK requiring product features. Select the fork only after checking its setup on the available Linux machine, current provider adapter boundaries, tests, migration effort, and license/data handling. Avoid copying implementation code across incompatible licenses; adapting behavior/patterns is safer than combining codebases.

Telephony providers, local number availability, identity/registration rules, and calling rates vary by country. The target country is India; see the verified requirements below. Irrespective of provider, expect a paid number/carrier and per-minute voice charges; free Gemini/Groq/OpenRouter API access does not make PSTN calls free. For a self-hosted Linux app, the provider must be able to reach it through a secure public HTTPS/WebSocket endpoint or a supported SIP/media service. During local development, a tunnel can expose the service; for an always-on production receptionist, use a stable, secured endpoint.

### India telephony constraints (researched 2026-10-25)

- Twilio's support article currently says it does not offer local or mobile Indian numbers. Twilio may support some international outbound reachability, but that is not a simple way to get the desired Indian inbound business number.
- Plivo documents Indian numbers and SIP trunking, but its current India guidance says the account must use the India data region, Indian numbers require business registration/KYC, and SIP plus media must terminate on infrastructure in India. Its compliance guide lists business incorporation/Udyam and GST documents for Indian local business numbers. Confirm number type and exact current requirements with Plivo before purchase.
- Plivo specifically documents LiveKit support with region pinning, so a LiveKit-based path is possible only when the project/media is pinned to India. For a self-hosted media server, verify the server is physically hosted in India and that the carrier accepts its SIP/RTP endpoint.
- This makes the generic "Twilio is simplest" assumption wrong for an Indian inbound number. A reasonable first route to investigate is a Plivo India SIP trunk/number into an India-hosted Asterisk/FreeSWITCH or supported India-pinned LiveKit path. It is not yet confirmed that the user's current machine, provider account eligibility, and target agent repo satisfy those requirements.

These India constraints affect the **carrier adapter and deployment plan**, not whether an otherwise strong international receptionist app/framework is worth adopting. Select the reusable product core on its call lifecycle, business workflow configuration, multilingual support, provider seams, and testability. Keep phone numbers, SIP registration, carrier API credentials, media-region/codec settings, and country-specific compliance as separate deployment adapters. Once a real number is acquired, validate the exact Indian provider and hosting route; do not prematurely reject a candidate solely because its default carrier example is Twilio or US-oriented.

## Long-term model and architecture agility requirement

The user also requires the system to stay easy to update as better voice models and open-source projects appear. This is an architectural constraint, not a promise that any framework automatically stays ahead of the field. Keep business workflows and phone control independent from the speech engine, and make voice engines selectable behind stable adapter contracts:

- **Realtime speech-to-speech engine:** accepts live audio, emits speech and events, and supports interruption/tool calls where available (for example Gemini Live or later engines).
- **Composable pipeline:** separate streaming or file-based STT, text LLM, and TTS adapters (for example Groq STT + a selectable Gemini/Groq/OpenRouter text model + Kokoro or a hosted TTS). This is the local/fallback and provider-comparison path.
- **Telephony/media adapter:** handles the carrier, SIP/WebRTC, sample-rate/codec conversion, call lifecycle, and barge-in without embedding model-provider logic in the business layer.
- **Capability declarations:** document for each adapter whether it supports streaming, interruption/cancel, transcripts, function calling, custom voices, languages, local execution, and required credentials. Do not pretend providers are interchangeable when one lacks a needed feature.
- **Provider-neutral evaluation:** preserve a fixed call scenario suite and record end-of-turn-to-first-audio p50/p95, interruption success, transcript quality, task success, failure/recovery rates, and cost per minute. Make a new model earn promotion by these results, rather than replacing a working provider based on release notes.
- **Versioned configuration and safe fallback:** select engine/model per deployment or call, keep local mode explicit, pin working provider versions, and never silently switch data from local to cloud. A change should be reversible without changing business policy or call routing.

### Reusable business profiles

The user expects the product to be adaptable to different businesses and languages. Prefer one shared codebase with reusable business profiles/templates instead of forking a separate application per business. A profile should hold verified business facts, services, hours/timezone, policies, supported languages/locale and voice, enabled tools (booking, transfer, callback, message taking), calendar/CRM integration configuration, and tenant-specific provider choice. If multiple businesses use one deployment, enforce workspace-level isolation for credentials, contacts, recordings, transcripts, knowledge, and logs. Country/carrier configuration belongs to the phone number/workspace boundary, while conversation behavior remains portable. A profile change should be testable with the same call scenario suite.

Kokoro is a text-to-speech model/runtime; Pipecat is a voice-agent framework that connects media, turn handling, and provider adapters. They solve different layers. A modular project could use a Pipecat pipeline with Kokoro today and add Gemini Live or a newer realtime engine later, while the receptionist's business and phone workflows remain in a separate layer. On this requirement, Patter/Pipecat/LiveKit offer stronger provider-swapping foundations, while a complete receptionist app offers more ready-made workflows. The best customization candidate must be inspected for both: a complete product shell plus a voice layer that can be swapped without rewriting the product.

[voice-receptionist](https://github.com/vinimabreu/voice-receptionist)** | Small multi-location clinic demo; MIT. | Excellent safety pattern: model proposes structured actions, deterministic booking code checks slots/ownership, FAQ has an abstention threshold, model failure routes to a human, and key-free scripted tests cover flows. Honest about 1–2 second Twilio turn-based behavior. | Tiny synthetic clinic demo, not a broad product; requires Claude and Twilio in its documented path. ### Frameworks and SDKs are a different category

- **[Pipecat](https://github.com/pipecat-ai/pipecat)** (BSD-2-Clause) is the strongest general Python voice-pipeline framework to evaluate for streaming, turn detection, barge-in, and provider changes. It is not a receptionist product: profiles, bookings, dashboards, staff workflows, persistence, and tenant controls must come from an application.
- **[LiveKit Agents](https://github.com/livekit/agents)** (Apache-2.0) is a strong session/media foundation for realtime browser and phone agents, including SIP. It is also not a finished receptionist app. DeskRoute and Tel-Agent demonstrate how it can be used in a product.
- **[Patter](https://github.com/PatterAI/Patter)** (MIT) is a promising voice SDK for connecting realtime model and carrier options, including Gemini Live and telephony. It is an SDK rather than the receptionist workflow/dashboard product we want.
- **[AI Native Call Center](https://github.com/rasonyang/ai-native-callcenter)** (Apache-2.0) is a more complete FreeSWITCH/call-center reference for queues, handoff, call records, and realtime provider gateways, but it is not as appointment-receptionist-oriented.

### Recommendation for this project

**Do not pick a winner from README claims alone. Run a bounded comparison between Voice Agent OSS and DeskRoute first, with LobbyStack as the product-depth benchmark.** These candidates cover the current fork decision:

1. **Voice Agent OSS is the strongest initial technical candidate** because it combines a Gemini Live phone runtime, adapter-based carrier choices, dashboard, MIT licensing, and business configuration. It also has an India telephony guide, but we should select it for its architecture and provider compatibility, not because its sample carrier is India-ready. The key validation question is whether the receptionist workflows are complete/reliable enough to customize, or whether this is mainly a well-structured starter.
2. **DeskRoute is the strongest complete appointment-business candidate** with a browser test call and a polished call-to-escalation workflow. It is closer to “fork a receptionist app,” but its AGPL-3.0 license, LiveKit/US-number assumptions, and lack of documented Gemini Live phone path are material trade-offs.
3. **LobbyStack is the strongest broad MIT product reference** for business setup, admin workflows, tests, local mocks, and appointment/transfer operations. Its OpenAI-specific realtime route is the largest voice-engine mismatch; estimate that swap before choosing it as the actual fork.

Keep the current project as a working diagnostics/reference surface during the fork evaluation. For each candidate, inspect the same vertical slice on a local Linux setup: clean install/build/tests, simulated incoming call, business-specific profile, no-answer/transfer path, one real tool action against a test calendar, interruption behavior, event/error logs, and how Gemini/Groq/OpenRouter or a future engine can be selected without rewriting business rules. Do not expose a test call page that can accidentally create real appointments without clearly labeling that behavior. Keep license, voice-model terms, database/runtime dependencies, and telephony-provider terms as separate checks.

**Market conclusion:** no single GitHub repository reviewed is both an obviously proven production receptionist, complete for our business needs, permissively licensed, and ready to use our preferred realtime Gemini voice plus any Indian carrier. Voice Agent OSS is the best compatibility/architecture candidate; DeskRoute is the best complete workflow candidate; LobbyStack is the best broad MIT product shell. A hands-on install and call-path review is needed to choose the base. India can be handled as a carrier/deployment customization after selecting the application core, as the user clarified.
